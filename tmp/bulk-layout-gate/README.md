## 次の候補として何を調べるか

保護対象は閉じたWasmモジュール内部のデータ配置とアクセスの対応。解析者は変換済みバイナリ、任意入力実行、メモリ観測を利用できる。秘密のランタイムや外部鍵を仮定しない。
配置を変えるだけでは既存手法と重複する。候補の未検証の焦点は、bulk操作の範囲制約と配置変換の選択を同時に扱い、通常の1byteごとの再マップ対照に比べて同じ解析課題を維持しながらコストを抑えられるか、である。
単なる高速化や既知の配列分割になれば、新アルゴリズムとして採用しない。

### 暫定規則

1. 論理バイト位置iを物理位置p(i)へ写す全単射を用いる。pはバイナリ内にあり秘密ではない。
2. load/storeはアクセス幅全体について論理境界を先に確認し、各バイトを再マップする。配置をまたぐ幅のアクセスを単一物理loadに置換してはならない。
3. memory.copyは元と同じ論理範囲の境界検査をすべて済ませてから変更する。重複コピーは論理アドレスの順序で方向を決定する。
4. コピー元・先の両範囲でpが順序を保つ連続写像であると証明できる場合に限り、1回の物理bulk copyを許す。この条件は十分条件であり、必要条件とは主張しない。
5. 静的に分かるbulk範囲を連続配置制約として扱い、残った領域の配置自由度と追加コストを計算する。実行時の値を見て正しさ条件を緩めない。

規則1-4自体の新規性を主張しない。規則5についても従来のlayout最適化やarray splittingとの詳細比較が必要。全範囲を連続にすると配置自由度が消えるため、最適化するだけで保護効果が残るとは限らない。
export/importされたメモリ、ホストが保持するポインタ、共有メモリ、grow、SIMD、atomic、例外は未設計。対応済みと扱わない。

## 小規模全探索による適用条件の確認

model.cjsは6バイトの全720置換と、正の長さを持つ91種類の有効コピー範囲を全探索する。
元の配列からのsnapshotコピーを参照にし、論理方向で1バイトずつ再マップするコピーを検証した。65,520比較、不一致0。
両区間が順序を保って連続する場合の物理コピーも27,179比較で一致した。
連続条件を無視した単純な物理コピーは28,256条件で不一致。最初の反例をresults.jsonに保存した。失敗数はこの誤った模型の結果であり、実在ツールの不具合ではない。

すべての隣接2バイト範囲を順序付き連続にする置換はidentityのみだった。一般にもp(i+1)=p(i)+1を全iに課すとp(i)=p(0)+iとなり、同じ有限区間への全単射ならp(0)=0となる。この条件下では全域の配置変更余地はない。
反転、別の物理領域、複数命令によるコピーまで不可能とする結果ではない。

このモデルはWasmを実行していない。ゼロ長、範囲外、trap後メモリ、32bit演算、性能は未検証。全探索は6バイトの抽象モデルについてだけであり、一般の意味保存証明ではない。
