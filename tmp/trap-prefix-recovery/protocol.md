# 書き込みログ復元：実行前の条件

2026-10-12。前回は意味保存の試作と実験を保存した進捗あり。今回は採用保留のtrap-prefix-fusionを解析面で反証する。

保護対象は各入力で元の領域が実行する有効store32の順序付きアドレス・値。最後のmemoryだけの一致では成功としない。完全に上書きされるstoreも数え、trap以降のstoreは含めない。元ソースや任意入力での式そのものの復元とは区別する。

解析者には候補Wasm、公開入力、初期memoryを渡す。元IR、元WAT、変換の対応表は渡さない。復元器を独立プロセスで実行し、そのコードはこれらを読まない。照合器だけが元IRを解釈する。

方式既知の静的ヒューリスティック: 唯一の5個のi32引数を持つ関数をforwarding helperと推定する。最後の3引数をアドレス・値・有効性として観測する。呼出しの入れ子を数え、最大のグループ（同数なら最後）を選ぶ。今回の候補には末尾のloadへ全ログを渡す構造がある、という知識を利用する。

WABTでバイナリをWATへ戻し、関数・ローカル名はツール生成名を使う。元の役割名は使わない。観測用importとglobalを追加して再アセンブルする。計測は既存raw/O2バイナリを対象に後付けする。計測用callbackは記録のみ行い、例外や外部操作を起こさない。

対象は13プログラム×raw/O2=26本、元の224入力。学習データを使う方式ではなく、各入力の実行からログを得る。正解データに合わせた観測列の並べ替え・選別は禁止。復元ログ全件に加えて、計測後の返り値・trap種類・最終memory SHAを元の実行記録と照合する。

26本すべてで正しいログが得られるなら、この具体案は保護対象を満たさず棄却する。helperがinline化された別設定、末尾loadがない領域、型署名が曖昧な場合へ一般化しない。未対応構造で復元器が止まることは候補の強度の証拠にしない。
