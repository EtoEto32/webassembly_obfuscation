## 想定していた具体的な規則L0

純粋なi32式 `v = op(a,b)` を、値を計算せず `node(op,handle(a),handle(b))` のハンドル生成に変える。値が必要になったときforceが依存先を評価し、結果をメモ化する。実際の分岐条件、公開出力、副作用を起こす処理の引数はforceする。ループの各反復は別のバージョンのハンドルを作る。

このままでは単なる式グラフのインタプリタである。演算ラベルの乱数化やノード配置変更だけを追加して新方式と呼ばない。グラフ書き換え等も、具体的な規則を定義せず「動的だから難しい」と主張しない。

## 限定的だが明確な復元方法

解析者がグラフのノード形式と演算ラベルの意味を理解し、対象の純粋領域のグラフを観測できる条件を考える。出力ハンドルから依存辺を走査し、各ノードについて演算と子ノードのIDを記録すれば、同じ計算を表すSSA形式のDAGを再構成できる。

有限の非循環グラフ、Vノード・E依存辺なら、訪問済み集合を用いた走査はO(V+E)でよい。共有部分を複製して式の構文木を巨大化させる必要はない。遅延・評価順の変更・メモ化だけはこの復元を妨げない。

これは既知のノード形式に対する設計上の論証。未知のWasmからノード形式を自動発見する実測結果ではない。分岐・ループの全経路を1回のスナップショットから回復できる主張でもない。ここで復元する対象は観測できた純粋領域の演算DAGであり、元ソース全体ではない。

## 意味保存に必要な制約

- i32の加算・乗算等の全域で定義された純粋演算と、除算・メモリ操作等のtrapし得る演算を区別する。
- 使われない結果の計算にもtrapがあれば、省略や遅延が元の挙動を変え得る。
- ロードを遅延するなら、途中の書き込み・ホスト呼出しで値が変わらないことが必要。初期値をノードに保存する方法は別の実装として区別する。
- グラフの記憶領域追加、スタック深さ、終了性も適用範囲に関わる。有限の算術式の正しさから、任意Wasmの正しさへ一般化しない。

trapと公開メモリの順序については、既存の [反例記録](../next-candidate-audit-2026-10-12/README.md) と `../next-candidate-audit-2026-10-12/artifacts/trap-state.json` を今回再読した。双方がtrapしても公開メモリ値が異なる反例が保存済みなので、同じ例を新しい実験として再生成していない。これは公開ツールのバグ報告ではない。

## 判定と次の作業

L0は新アルゴリズム候補として採用しない。既存の実行モデル変更との違いが未確立で、単純な表現では計算グラフが残るためである。効果が未確立のまま大規模ベンチマークを増やさない。

次に必要なのは、命令を隠す場所を移すことではなく、解析者が使う観測上の対応関係をどの具体操作で変えるかの設計である。先行研究のDataMeldはVM管理状態とプログラム状態の区別を扱う可能性があるが、現時点では検索抜粋しか確認していない。一次資料の具体的な規則を読むまでは、データ状態と管理状態の混合を新しい案として採用しない。

既存候補の棄却数は成果達成の代替ではない。有望な独自変換、対応する実装、公平な比較実験、採用判断が引き続き未完了。
