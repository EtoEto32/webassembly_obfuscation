## 静的に確認できた具体的な処理

|箇所|コードから確認したこと|今回の設計への含意|
|---|---|---|
|MathUtils.hの型定義|UINT_TYPEはuint8_t、INT_TYPEはint8_t|今回の取得版を32bit汎用RNCとして比較しない|
|RNC.h:12付近|RNC_RAND=1|ランダムなmodulus倍の追加を含む設定|
|RNC.c:73 encode|各modulusで剰余を求め、設定に応じてaddRandを呼ぶ|正規化された剰余だけを保持するとは限らない|
|RNC.c:136 AddEnc|成分を剰余へ戻して加算し、LessEncによる範囲判定後にOverflowShiftとAddEncで補正する|補正なし演算とは区別が必要|
|RNC.c:159とRNC.hのAddEnc宣言|加算についてm1*m2>510という条件が記載される|入力を表せるM>255より強い条件がある|
|RNC.c:36 OverflowShift|255を使った符号化値を構成し、SubEncを呼ぶ|型マクロを変更するだけでは一般のwビット実装にならない|
|RNC.c:229付近 LessEnc|拡張Euclidと混合基数の桁を用いて比較する|「比較には必ず元の整数を丸ごと復号する」とは言えない|
|RNC.c:119 MultEnc|成分の乗算とaddRandがあり、この関数本文にはAddEnc同様の明示的な範囲補正分岐はない|乗算の保証範囲は呼出し側・型・modulus条件も含めて確認する必要がある|

最後の点から直ちに著者実装の不具合とは判断しない。呼出し側の全用途を読んでおらず、元のCを実行していない。ビット演算用の限定値を扱うことと、任意の二つの8bit値の乗算を保証することは別である。

## 前回の実験との対応

[residue-wrap-gate](../residue-wrap-gate/README.md)は自作Wasmの補正なし演算を試験したもの。今回のコード照合により、それをHOACSの補正方式そのものへの反証として扱えないことが一層明確になった。元の記録も著者実装のバグ報告とはしていない。

M>最大入力、M>二入力の和、M>積、複数演算をまとめた領域の整数上の上界は、それぞれ違う条件である。今回の将来候補は、比較対象を不正な補正なし版だけにせず、既存の補正を含む方式と比較する必要がある。

## 候補設計で残る差分

「各演算で補正する」対「範囲を証明した複数演算の領域だけ補正を遅らせる」という比較は定義できる。ただし、それだけで新規難読化とは認めない。一般の遅延剰余削減・範囲解析・データ符号化との具体的な違いが未確認である。

次にこの方向を進める際は、加算・乗算に加え、i32の中間値を観測する分岐を境界として扱い、どこに補正が必要かを明示する。性能が良くても復元が容易なら、難読化の有効性とは区別する。現在はまだ具体的な採用候補を確定できていない。
