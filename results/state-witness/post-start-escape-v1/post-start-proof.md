# 起動後の寿命差が読まれないことの十分条件

手書きの論証であり機械検証ではない。前提は[実験計画](post-start-plan.md)の通り。

時間・resource使用量/OOMを観測から除き、その他の内部非決定的選択を対応付ける。物理的なsegment領域の解放がallocation成否へ及ぼす影響まで、このstore意味論で証明するものではない。

内部関数に実行が入る経路は、exportからのhost call、direct/tail call、関数参照によるindirect/ref call、または既存frameからの再開である。最後の経路を前提で除く。最初の経路はroot、二番目はcall閉包に含まれる。三番目の内部関数参照は、moduleのexportまたはliteral ref.func/element関数参照に由来する。別instanceやhostが参照を保管・再返却しても由来は変わらないため、過大近似したroot集合が覆う。関数型が一致するだけでは非公開の内部関数参照を生成できない。

到達集合に6種のsegment readerが一つもなければ、将来の実行はsegment内容・長さを読まない。segment dropは対応する状態を両実行で空にするだけで、結果値もtrapも生じない。その他の命令は同じ非segment状態と同じhost選択から同じ遷移を取る。この不変条件を各遷移へ延長すれば、正常終了、trap、host呼出し、公開store観測に差は生じない。発散に対しても各有限prefixを対応付けられる。

この議論は寿命が違う任意のsegment集合について成立する。一方、readerがreachableなら、実際にはlen=0、同じdropが先行する、条件分岐が常に偽、private storeだけが変わる等で観測不能なことがある。本検査はそれらを「不明」に残す。反例検査器Kへ進む余地はここにあるが、全プログラムをKが受理するわけではない。

これは通常の到達可能性と非干渉に基づく十分条件であり、独自の解析原理や復元器全体の正しさを証明したという主張ではない。
