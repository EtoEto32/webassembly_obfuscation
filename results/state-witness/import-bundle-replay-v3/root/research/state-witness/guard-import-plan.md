# 同期void importを含む限定診断：実装前の計画

実装後の用語明確化（2026-10-24）：この計画のwriteは全対象cellへの必須共通代入として実装・検査された。「書ける」を一般的なmay-write権限と読むと範囲が広すぎる。[後続計画](guard-import-may-plan.md)で省略・部分書込みを別に扱う。旧の計画と実験を後からmay-writeの結果へ変更しない。

2026-10-24。従来の閉じたparserを変更せず、別の明示的profileとして試す。実復元器で得たentry内host書込みの差を、手作業の説明だけでなく条件生成へ接続することが目的である。一般的な環境遷移・関係WPの新規性は主張しない。

受理するのは、引数・返値なしの同期function import、定数bulk memory/table操作、drop、直線的void exportである。host契約は各importが公開resourceを読めるか・同じ任意値を書けるかを指定する。hostは正常returnし、再入・grow・外部I/O・任意関数呼出しを行わない。import名と順序を常に観測し、read契約なら呼出し前の公開storeも観測する。write契約ならその位置で共通代入を普遍量化する。

左右をそれぞれ次のimportまたは関数終了まで進める。片側がtrapし他側だけがimportへ到達すれば、最終的に両側がtrapしてもtrace差である。同じimportへ到達した場合は、その位置の公開store比較とhost代入を含めて後続条件を逆伝播する。API外だけに書込みを許すモデルやimportをnopにするモデルでは、この契約を表現できない。

初期版の成功条件：

1. 実際のimport付きbinaryを入力でき、未指定host契約や非void importを明示的に拒否する。
2. write前後の配置、read境界、片側だけのimport、修復、0長の対照をNode/Wasmtimeで検査する。
3. importの各位置に別の任意入力を置いたarray式で一段の条件を検査する。
4. 実復元器のentry実験との対応は、抽出した継続部分と元program全体を区別する。活性stackや再開PCを解析したと主張しない。

最初は条件合成を実装する。import入力を含む最短反例は従来の一括host入力と長さの定義が変わるため、自動的に継承したとしない。否定時は具体入力をSMTで求め、実行して検査する。最短性は主張しない。結果に合わせた成功条件の後付けを避けるため、この計画をコード実行前に保存する。
