## 目的と判断

RQ1で確認した変換の仕組みを基に、RQ2で調べた出力・構造・速度との関係を対策の評価にも用いる。採掘処理が存在することと、利用者の同意のないクリプトジャッキングは区別する。ここで扱う手法では、同意の有無をWasmだけから判断できない。

単純なNOP挿入と整数定数分割には、局所正規化を解析前処理として採用する。複雑な整数式には、コードを書き換えない式比較を併用する。平坦化については、既知のモデルが扱える範囲で処理の対応を比較するにとどめる。一般的な平坦化の解除、検知器としての採用、検知率の改善は、達成した成果に含めない。

## 1. NOP除去と整数定数式の畳み込み

### 機構と処理の流れ

NOPは、通常の実行では値やメモリを変更しない命令である。整数定数分割では、1個の定数を複数の定数と演算で表す。例えば、32ビット整数の `7` を `3 4 add` で表した箇所は、3命令を `7` にまとめられる。負数や桁あふれを含む場合は32または64ビットの剰余演算で計算し、同じビット列を持つ符号付き定数の表記に戻す。

処理は `Wasm → WABTの線形WAT → 局所規則 → WAT → Wasm → 検証` の順で行う。書き換えたWasmと、規則・関数・元の行・変更前後の内容を記録したevents JSONを出力する。基準バイナリ、ファイルSHA、変換位置ログは、正規化の判定に使わない。

実装は[normalize_wat_local.py](C:/Users/ettotto/Documents/webassembly_obfuscation/scripts/normalize_wat_local.py)である。適用する規則は、関数内の独立したNOP行の除去と、字下げ・関数・ビット幅がそろった連続命令 `const const op` の畳み込みに限る。演算はadd/sub/mul/and/or/xorだけを扱う。後者は入力2値を消費して結果1値を積むため、対応する定数1命令とスタックへの作用が一致する。繰り返し畳み込める定数式は、そのまま続けて整理する。

### 適用条件と意味の確認

浮動小数点、除算、シフト、トラップを起こす演算を含む式や、分岐・呼出し・メモリ操作を挟む式、folded WATは書き換えない。一般的なSSAや制御フローの復元も実装していない。正規化できることは、元のコードが難読化されていたことを意味しない。通常のプログラムにも定数式は存在する。

安全性は、各確認で分かる範囲を分けて評価する。WABTの検証では型・構造が仕様に適合すること、import/exportの照合では呼出し宣言が保たれること、自作整数テストでは有限個の入力に対する局所規則の結果、採掘テストベクトルでは選定した入力に対するプログラム全体の出力を確認する。いずれか1つだけで、すべての入力・ホスト条件での同値性を証明したとはしない。

確認済みの結果には、自作912関数の局所テスト、SWAMPEDの開発用2変換版と別の乱数・変換量による8変換版での両規則適用後のバイト列の一致、通常標本と計測標本への静的適用がある。A-Star・CreaturePackの通常版と計測版の計4件は専用規則で変更されなかったが、通常のbase64-cli・seqtkの定数式は畳み込まれた。これを悪性の誤判定や検知成功としては扱わない。

再現用スクリプトは[開発比較](C:/Users/ettotto/Documents/webassembly_obfuscation/scripts/evaluate_local_normalization.py)、[別標本比較](C:/Users/ettotto/Documents/webassembly_obfuscation/scripts/evaluate_normalization_transfer.py)、[別乱数比較](C:/Users/ettotto/Documents/webassembly_obfuscation/scripts/evaluate_seeded_normalization.py)である。いずれも静的な変換・検証を行い、採掘用Wasmは実行しない。再実行すると既存結果を上書きする可能性があるため、保存した測定との対応を保てるよう、対象ファイルを上書きせず別runで再評価する。

この規則自体は既知の局所簡約であり、新しい難読化解除アルゴリズムとは主張しない。適用箇所を説明でき、書き換える範囲を狭く制限できる点を評価し、解析支援として採用する。一般的な検知器としては採用しない。

## 2. 既存最適化との比較

Binaryen version 133の `--vacuum --precompute` と `-O2` を固定して比較する。局所passと全体最適化を区別し、基準版にも同じ処理を適用する。入力には同じWasmを用い、最適化したWasmと静的指標を出力する。

整数定数分割版は、既存最適化でも同じ処理を施した基準版と一致した。NOP版の最適化後に残った差を調べると、NOP数は0で、他の命令が異なっていた。基準版のバイト列と一致しないことだけで、既存最適化がNOPの除去に失敗したとはいえない。O2ではimport関数やglobal宣言が減る条件もあった。こうした変化を、専用規則による局所的な変更と同じ効果として合算しない。

6入力×4処理×6反復の前処理時間を比較した。計時範囲には、入力読み込み、ツール起動、変換、出力書き込み、WABTによる検証を含めた。専用処理は局所最適化より時間を要した。この時間はPythonとCLIの間の呼び出しや実装構成にも左右されるため、アルゴリズム自体の優劣を示してはいない。今回の実験から、専用処理の高速性や一般的な優位性は主張しない。

根拠：[処理時間の報告](C:/Users/ettotto/Documents/webassembly_obfuscation/docs/countermeasure-processing-time.md)、[最適化残差の記録](C:/Users/ettotto/Documents/webassembly_obfuscation/results/countermeasures/seeded-normalization/optimizer-residual-review.json)。公式説明は[Binaryen README](https://github.com/WebAssembly/binaryen/blob/main/README.md)。公開説明の最新版と、今回固定した実行ファイル・SHAを区別する。

## 3. 書き換えを行わない整数式比較

### 機構と原理

整数演算置換では、変数を含む複数の算術・ビット演算が、単純な演算と同じ結果を表すことがある。定数だけの畳み込みではこの対応を扱えない。そこで線形WATのスタックとlocal.get/set/teeを追い、式の木を抽出する。

入力の各ビットをBoolean変数として扱う。ビットごとのANDは積、ORは `a+b-ab`、XORは `a+b-2ab` に対応し、`b*b=b` を用いて多項式を整理する。32・64ビット整数の剰余演算で係数を計算し、得られた式が `x << s` の多項式と一致するか比較する。変数名や関数番号の一致ではなく、対応する整数式の表現が根拠になる。

入力はWATである。出力には、関数、行範囲、出力先local、ビット幅、式、対応するシフト量と、未対応理由ごとの件数を含める。元のWasm、制御構造、メモリは変更しない。

### 適用範囲と判断

独立変数1個、12～80ノードの式だけを扱う。ビット演算の子に算術式がある場合、非定数シフト、複数入力に依存する式、展開上限を超える式は対象外とする。分岐、メモリ操作、呼出し、未対応命令に出会うと、依存関係の情報を破棄する。制御フローを越えて同値性を推定しない。

xmrの仕組みを確認した標本で43件の式を出力した。Cryptic Bytesでは10プログラム・3設定・2ビルドの計60件を調べ、未最適化LLVM版10件で計140件の式を出力した。抽出した183式に有限個の入力、計19,398件を与え、独立した整数評価器で照合した。式の範囲に重複があるため、183個の独立した変換としては扱わない。Tigressの5,018候補は複数入力に依存するため対象外だった。最適化後の出力が0件でも、難読化が完全に除去されたことを意味しない。

局所正規化では複雑な変数式を整理できなかったため、対応箇所の説明を補う方法として採用した。元のWasmは書き換えないが、識別した式が測定入力で実行されるかは別に確認する必要がある。通常の式にも恒等式が成立するため、悪性の分類には使わない。

実装は[analyze_integer_expressions.py](C:/Users/ettotto/Documents/webassembly_obfuscation/scripts/analyze_integer_expressions.py)である。このスクリプトに入力WATと出力JSONを渡して再現する。複数標本を比較する場合は[evaluate_integer_expression_analysis.py](C:/Users/ettotto/Documents/webassembly_obfuscation/scripts/evaluate_integer_expression_analysis.py)と[evaluate_cryptic_expression_transfer.py](C:/Users/ettotto/Documents/webassembly_obfuscation/scripts/evaluate_cryptic_expression_transfer.py)を用いる。保存済みの解析時間は1回だけの測定であり、安定した性能を示す評価ではない。

計時したのは、WATを読んだ後のextract(text)の呼出しだけで、WABTによる検証、逆アセンブル、書き込みは含めない。保存された24条件では55.4～1,153.6 ms、Cryptic Bytesの60条件では112.5～976.0 msだった。命令の表現や式の展開量に左右される1回の観測であり、繰り返し測定した前処理時間や採掘速度とは区別する。

式簡約の発想には[MBA-Blastの一次論文](https://www.usenix.org/conference/usenixsecurity21/presentation/liu-binbin)と[公開実装](https://github.com/softsec-unh/MBA-Blast)がある。本実装はMBA-Blastの再実装ではなく、その実行比較や優位性評価も行っていない。

## 4. 平坦化の限定状態モデルと実行経路

平坦化では、処理の順序を状態値と分岐で表す。命令数を減らすだけでは、通常のループとの対応を説明しにくい。既存解析で確認した8・16バイトXORの4状態について、状態番号ではなく「初期化・読み込み／XOR／書き込み・更新・終了」という処理の役割と遷移を比較した。

この比較では、事前に解析したモデルを入力する。未知のWasmから状態や役割を自動推定する実装ではない。モデル上の処理の役割の列と、逐次XORによるメモリ更新が一致する範囲を確認する。通常版と平坦化版から2関数ずつ切り出した小さなWasmで、重複ポインタ等を含む698ケース・1,396呼出しを照合した。メモリは一時スタック32バイトを除いて比較し、スタックポインタも確認した。

モデル固有の状態値を一般的な解除規則へ埋め込む方法は採用しない。自動復元、モジュール全体で意味が保たれること、採掘速度改善の証拠ではなく、限られた範囲で処理の対応を説明するための比較として残す。再現用のコード・資料は[check_reviewed_state_models.py](C:/Users/ettotto/Documents/webassembly_obfuscation/scripts/check_reviewed_state_models.py)と[check_isolated_xor_controls.cjs](C:/Users/ettotto/Documents/webassembly_obfuscation/scripts/check_isolated_xor_controls.cjs)、根拠は[状態モデル結果](C:/Users/ettotto/Documents/webassembly_obfuscation/results/countermeasures/flattening-xor/state-model-checks.json)。

RQ1の経路解析とRQ2の入力を照合する方法も併用する。変換された関数が対象入力で実行されない場合、その静的な命令増加を測定速度低下の原因としない。経路の対応は選定した入口・条件に限り、すべての経路の網羅や未知標本の自動検知ではない。JIT・生成機械語を直接確認していないため、速度差の細かな原因は未確定である。

## 5. 固定検知器による予備比較と特徴の消失

MINOSの公開再実装では、バイト列を画像に変換してCNNに渡す。今回のアダプタでは、公開重みの層と数値配列を確認してモデルを明示的に構築する。元のWasmは実行せず、2クラスの確率、logit、argmaxによる判定を保存する。分類確率を整数化した終了コードは、クラスとして使わない。

独立したNumPy計算で8入力を照合し、前処理も4条件で照合した。その後、対象と判定規則を固定して144条件を推論した。公開ソース内に画素の尺度が0～255と0～1の経路があるため、両方の条件を固定して比較した。21条件で予測が異なり、専用規則を適用した72条件では、どちらの尺度でも正規化前後でクラスが変わった条件は0件だった。通常コードもMALIGNと予測された。訓練の経緯、訓練データとの重複、重みの学習時に用いた尺度は未確定のため、一般的な適合率・再現率や検知の改善は算出しない。

専用規則を適用した72条件のうち10条件ではNOPがなくなり、NOPの有無を表す特徴が失われた。36条件では命令総数が変化した。分岐・呼出し・メモリ操作の命令数は種類ごとに保たれたが、制御構造全体や特徴の比率が保たれることを意味しない。正規化によって分析しやすくなる一方で、難読化を示す元の特徴が消える可能性がある。このため、原本・正規化結果・適用記録を併用する。

MINOSは固定モデルへの影響を確認するために用い、今回の成果を検知器の完成としない。MinerRayは公開パーサと依存関係・実行条件を調査したが実行比較は未実施、WASimはLFSポインタと実モデルの違いを確認した段階である。これらの手法が不可能・劣ると結論しない。外部送信を伴うVirusTotalは今回の比較対象に選ばない。詳細な一次ソース、固定コミットとSHA、実装・再現用のコード・資料は[検知器適用可能性の報告](C:/Users/ettotto/Documents/webassembly_obfuscation/docs/countermeasure-detector-feasibility.md)と[source-manifest.json](C:/Users/ettotto/Documents/webassembly_obfuscation/results/countermeasures/detector-feasibility/source-manifest.json)。

## 6. 実際のハッシュ出力と速度による検証

専用規則と既存最適化は、基準版、難読化版、同じ処理を施した基準版を含む72条件で比較する。測定対象は、SHAが異なる23種類のバイナリにまとめる。同じSHAの条件には同じ測定値を対応付け、独立標本数を増やさない。公表された5入力では独立した期待値と照合し、追加した12入力では未処理の基準版の出力との差を確認する。

基準版の1／8／32バイト入力では、コンテキストを再利用した際に入力順序によって出力が変わることを確認した。このため追加入力は、新規コンテキスト同士と、公表入力の履歴・追加入力の順序をそろえた再利用コンテキスト同士で比較する。入力を除外せず、順方向・逆方向それぞれの基準出力を使う。原因は未特定であり、通常のCryptoNightにおける短入力の正しい出力や正規化の欠陥を確定したものではない。

教員の許可を確認後、ネットワークnone・CPU1・メモリ1GiB・最大2時間の隔離環境で実行した。Node/V8・ホスト・入力・1ワーカーを固定し、3秒以上ウォームアップしてから30秒以上の測定を6回繰り返した。巡回ごとに対象の順序をずらした。速度は、完了したハッシュ計算数を実経過時間で割って求める。正常終了、SHA、出力、全138ブロックを監査してから集計した。

公表された5入力の独立した期待値との照合、追加した12入力の新規コンテキストと同じ履歴で再利用したコンテキストでの比較、138ブロックの計測前後・最終出力の照合で、不一致はなかった。両規則適用後の速度の中央値を未処理版の中央値で割った比は、開発NOP版で1.0276、整数定数分割版で0.9943、別乱数8版で0.9827～1.0120だった。両規則の適用後は同じ基準SHAの測定値を共有するため、独立した復元標本を何度も測った証拠とはしない。

出力が一致したことを全入力での同値性、測定範囲が重なったことを統計的同等性、命令数が減ったことを高速化や検知の改善と読み替えない。基準版自体にも26.5502～32.0761 H/sの変動があり、専用処理による一貫した速度向上は確認できない。解析前処理としての限定的な採用は維持するが、速度や検知の改善を理由には採用しない。複雑な式にコードを書き換えない比較を併用する判断は、局所規則の適用限界に基づく。手順と生ログは[実行計画](C:/Users/ettotto/Documents/webassembly_obfuscation/docs/countermeasure-runtime-plan.md)を参照する。論文更新は今回の作業範囲に含めない。
