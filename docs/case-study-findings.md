# 個別ファイルの解析で確認したこと（第1段階）

2026-10-06時点。公開データセットの取得と全体解析は継続中であり、本書は中間結果である。20種類のバイナリについて、逆アセンブルの指定箇所、公開インターフェース、必要に応じて比較するもう一方のファイルとの差分をCodexが個別に読んだ。人間による独立レビューは未実施である。

## 選定対象と確認範囲

SWAMPEDの実験用の元ファイルと、WasmMalのルートディレクトリに含まれるファイルのうち、静的解析に成功したものを第1段階の選定対象とした。乱数シードは20261006。SHA-256で重複除去し、SWAMPEDに含まれるファイルは、優先的にそのグループへ割り当てた。生成元が不明なWasmMalのファイルは、参照データセットとの完全一致の有無で分けた。「参照データセットと非一致」は、人工的に生成されたと確定するラベルではない。

解析失敗4種類はこの枠に入らず、[選定記録](../experiments/review-selection-stage1.json)に残した。元の計画にある「参照一致でSWAMPEDに含まれない悪性」のグループは0件だった。選定対象の全件とハッシュは `experiments/review-frame-stage1.json` に保存した。以降に追加取得するデータセットは別段階で選定する。

この層別選定は、特徴的な事例だけを意図的に選ぶことを避けるためのものだが、レビューは指定箇所に限定される。20件中の候補数から全体の難読化率やインターネット上の流行率を推定していない。全関数を確認した小さなファイルを除き、モジュール全体に難読化が存在しないとは結論しない。

## 1. 悪性ラベルが付いた元ファイルにも計測コードが含まれる

`aafff587…` は、SWAMPEDのMalware_31、WasmMal、WasmBench、SEISMICに同一バイト列で含まれる。SEISMICでのパスは `CoinHive/64-bit/cryptonight_obfuscated.wasm` である。

関数77〜86は、グローバル変数11〜15から命令カウンタの上位・下位部分を返す。関数87はそれらを0に戻す。命令本体には `global.get N; i64.const 1; i64.add; global.set N` が繰り返される。

|対象グローバル|対応するカウンタ|更新パターン数|
|---|---|---:|
|11|i32.add|1,573|
|12|i32.and|302|
|13|i32.shl|1,077|
|14|i32.shr_u|523|
|15|i32.xor|576|
|合計||4,051|

4命令の更新列は合計16,204命令で、デコードした静的命令数47,033の約34.45%を占める。これは静的なコード構成の割合であり、実行時の命令頻度や実行時の負荷ではない。

[固定コミットのinline_counter64.py](https://github.com/wenhao1006/SEISMIC/blob/87f52c92eddadb2b786669f3a79582161f1c5c18/CoinHive/64-bit/inline_counter64.py)は、上記5種の演算に対して同じグローバル変数を増やす命令を挿入する。スクリプトはテキストとして読み、実行していない。

この事例では「参照データセットにある元ファイル」と「実際に配布・利用された、加工していないファイル」を同一視できない。冗長コードの量や命令分布を分析する際は、計測コードの影響も考慮する必要がある。一方、`thginotpyrc`という逆順の識別子も存在するため、計測コードがあることから他の難読化がないとは言えない。

根拠：[個別記録](../results/cases/aafff58765c917b0900726ecca11c715c38c3c25b1be9e0af130e0f5b170c14e/review-stage1.md)。この特性を全体でどの程度共有するかは、次の集計課題である。

## 2. br_tableの大きさは平坦化の根拠にならない

`23b65971…` の関数37では、浮動小数点のビット表現を52ビット右シフトし、2047でマスクしてから分岐表を参照する。これは倍精度浮動小数点数の指数部を選択値にしている。

分岐表にはデフォルトを含め2,049個のラベル要素があるが、分岐先の深さは3種類だけで、2,047個が同じ深さ2を指す。分岐表の要素数と、異なる行き先の数は一致しない。この箇所の巨大な表を、制御フロー平坦化用の大きな分岐処理と解釈する根拠はない。

他の複数ファイルでは、文字`%`の比較、ポインタの更新、1バイト読み込み、文字値から65を引く処理に分岐表が伴う。文字列・書式解析や共通ライブラリという説明を検討する必要がある。

根拠：[個別記録](../results/cases/23b65971ea3acdd776ef83ada9ab80ebd915ef49d82d6f7da4e11298cb9270be/review-stage1.md)。

## 3. 全体ハッシュが異なってもコードの大部分が一致する

|比較したSHA-256接頭辞|同一の関数本体|データ領域|観測した差|
|---|---:|---|---|
|c1be4071 / 65debcbe|59/59|異なる|コードセクション全体は完全一致。exportの識別子などが異なる|
|22a8da39 / 4ab6ed5e|57/59|完全一致|関数40と71に局所的な命令列の差|
|2eb0e7c2 / 1d38d08e|53/54|完全一致|関数39に局所的な命令列の差|

2組目では、ゼロとのxor、ゼロの減算、定数を積んでdrop、同じ値同士のandを確認した。3組目では、ポインタ値に対するゼロの減算とゼロビットの右シフトを確認した。これらが局所的に値を変えないことは命令の意味から説明できる。

ただし、この比較だけではどちらが変換前のファイルか、生成元のファイルが同じか、同じマルウェアファミリーに属するか、モジュール全体が同じ動作をするかは証明できない。WasmMalの論文が説明する生成過程と、元ファイルと変換後のファイルの対応の証拠を分けて扱う。

差分は[比較結果](../results/cases/pair-comparisons/pairs.json)と各diffに保存し、`scripts/compare_review_pairs.py` で再計算できる。

## 4. データを格納する小さなモジュールと通常の最適化も区別する

悪性ラベル付きの`67d25014…`は428バイトで、唯一の関数は`(16 - 0) >> 0`に相当する値を返す。データ領域には読み取れるHTMLがある。冗長な定数演算は確認できるが、大きな悪性処理がWasm内部に隠されている証拠にはならない。JavaScript側の利用箇所が未確認なので、処理をWasmへ移す難読化と断定しない。

良性ラベル付きの`0443e3e3…`は、2つのバイト値の差から符号マスクを作り、xorと減算で絶対値を求めて足し合わせる。4回分を展開したループと端数処理があり、`sad`というエクスポート名とも整合する。xor・シフト・反復だけを難読化とみなすと、通常の演算処理まで候補になる。

`85a47a86…`という別の良性ラベルが付いたファイルには、nop、ゼロの減算、無条件分岐の後に到達しない命令列が見られた。冗長な構造の存在も、単独では悪性や意図的な難読化の証拠にならない。

## 残る検証

第1段階20件に[第2段階の対照11件](control-study-findings.md)を追加し、計31種類を個別確認した。件数は30〜50件の目安に達したが、全データセットを漏れなく確認したことや人間の独立レビューを保証しない。今後は、JS/Wasm連携、Android、解析失敗などの追加確認を行う。元ファイルごとの集計、類似度の閾値による結果の変化、計測コードの分布、全体の図表も整理する。機械的な参照検査の成功は、各判断の独立した科学的検証の代わりにはならない。
