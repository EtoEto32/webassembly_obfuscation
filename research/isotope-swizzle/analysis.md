# 実測値の意味と失敗原因

今回の保護目標は、配布 Wasm 内の符号化された二入力表から、小さな等価な演算表現を回復する費用を増すこと。元の seed や置換そのものの特定、原ソースと同じ構文の再現は要求しない。攻撃者は方式と実行仕様を知り、配布バイナリを読む。関数の外部出力自体も観測可能なので、小さな一演算ベンチマークはブラックボックス同定も容易である。これらを実用アプリ全体の保護の証拠にはできない。

生値は performance-v1 の native.json/analysis.json、対応比較は report-v1 の pairs.json/csv。正規化部分だけの対照比は約10.8–22.1倍であり、解析費用の増加がゼロだったとはしない。ただし対照は表を正規化しない短い走査である。元の全単射を探索せず、1表あたり4096の結合律確認と256対の復元確認で済み、表数に応じて分割できた。これは「全件解除できたから無効」とだけ判断した結果ではない。

変換は約58.3–64.0msで、生成本体約0.35–1.32msに対し、source reader・assembler・validatorの起動費用が大きい。各生成条件の単回値で、変換時間の反復統計ではない。測定processの peak RSS 中央値は39,908–40,244KiB。Node全体の値であり、変換による増分の正確な測定ではない。宣言線形メモリは全て0 byte。JITの機械語・stack・コード定数の物理占有量は分離測定していない。

## 原因

非線形でランダムな表でも、左右の入力と出力を別々の全単射で変換しただけなら、元の演算の同位体の範囲に留まる。add/sub/xor の今回の表では、原符号化を探す前に行と列を基準化できる。最適化器が複雑な表をそのまま残すことと、解析者が等価な小表現を構成できないことは異なる。

元の表現の秘密を探す課題を置くと、不要な置換探索の費用を保護効果と誤認する。今回の攻撃は等価な任意の座標を選べばよく、その座標で短い式へ置き換える。回復後にも置換は残るので「完全に元コードを復元」とは呼ばないが、表への融合で増やした主な実行・サイズ負担は取り除ける。

先行性も強い。符号化表の合成と SIMD の小表参照を新発明とはできず、今回の追加配置規則による優位性は未確立。さらに大きな表・seed数・演算数へ増やすだけではこの失敗原因は変わらない。主特許候補としては不採用とする。

## 次の設計への条件

次案は、単一ゲートごとに小さな意味表現を回復できるかを、まず検査する。左右の独立な符号化を非分離な表現へ置換する場合も、その生成・解釈処理を攻撃範囲に含める。以前の joint-representation-screen が示したように、共同表現にするだけでも十分ではない。入力数や冗長さを増やすだけを別原理と数えず、具体的な回復課題と同程度の実行費用の対照を先に定義する。これは次案の採用条件であり、新方式を既に発明したという記録ではない。
