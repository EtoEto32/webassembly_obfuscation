# 草稿追補：型を重ねる格納領域再利用の限界

## Abstract

Wasm線形メモリの定義済みの非整列アクセスを使い、互いに干渉しない幅の異なるセルを部分的に重ねる配置を検討した。実Wasm変換と通常の再利用を比較し、3合成kernelの正36条件943,104呼出しが一致した。静的な型矛盾は増えるが、byteの到達定義を追う方式既知解析でraw/O3全18条件を回復できた。既存の格納領域共有から独立した新規性と大きな保護優位は未確認である。

## Introduction / Motivation

公開逆変換を含む値符号化の失敗から、格納場所の時間的な役割変更を検討した。固定アドレスへの型割当を乱すことと、計算内容を回復する費用を増やすことは別である。本実験はその区別を検証する。

## Related Work

LLVM StackColoringは生存区間が重ならない領域の統合を実装し、小領域を異なるoffsetへ統合する方向にも言及する。LLVM MemorySSAは書込みの到達関係と分岐での合流を扱う。一次資料の確認範囲は[照合記録](prior-art.md)に示す。今回の目的関数やWasmへの適用だけを新規性と扱わない。

## Threat Model / Proposed Method

全binaryと方式を知る解析者を想定する。アドレスと幅からセルを同定し、構造化ifの逆向きデータフロー解析で干渉グラフを作る。同時に必要な値は重ねず、作業領域を広げない範囲で異なる幅の重なりを増やす。入力は初期memoryを読まず、定数アドレス、private固定memoryと非trap整数演算に限定する。

## Implementation / Evaluation

Python変換器、WABT1.0.42、Binaryen133、Node24.15.0を使う。通常のfirst-fitと比較するが、LLVM本体を実測した対照ではない。O3の型衝突優先/元版実行時間は約1.01–1.06。3 fresh processと各7batchを測り、値・trap、別WABT実行、再生成byte一致、対象外拒否を検査した。[数値と生ログ](../../results/invention-20261022/lifetime-overlay-report-v1/comparison.md)を参照。

適応的回復は元source・配置表・oracleを読まない。全loadのbyteがどのstore値を表すかを追い、分岐では一時localへ合流値を代入する。全18条件を回復し、型衝突優先の総時間中央値は約38–45msだった。16段のdiamondでも合流16個で済んだ。正当性検査の全65,536パターンと解析での探索回数を混同しない。

## Discussion / Limitations / Conclusion

O3 diamondで回復本体の中央値はfirst-fit比約10.6%増えたため、追加費用が皆無とは主張しない。一方、既知の到達定義追跡で機構を説明でき、全経路を区別する必要もなかった。動的aliasや一般Wasmの難しさへ拡張して解釈しない。

本方向は通常のメモリ再利用に近く、独立した難読化アルゴリズムとしての新規性は未確立である。現段階で特許候補の主発明には採用せず、アドレスごとの型矛盾や経路数が保護の代替指標にならないという負の結果を残す。
