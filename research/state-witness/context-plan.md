# 残存segment差の意味を調べる追加計画

2026-10-24。cut実験の18回の「segmentのみ相違」を見た後の探索的追試である。独立した未見評価とはしない。

## 問いと事前の予測

中断後のguest storeを同じ元moduleへ写し、元のexport関数だけで呼び出しを続けたとき、segment寿命差が観測可能か。`memory_init/suite.3`由来の4中断では次の`test`が反例になると予測する。他の14中断はdrop以外から寿命を読む前にdropで揃うため、その差だけでは元APIを区別できないと予測する。

この予測は既に読んだWATに基づく。件数を発見率や未見精度として報告しない。

## 解析と実行

1. 元binaryの全export関数について、異なるsegment集合を入力に、命令を順に解析する。dropで差を消す。差の残るsegmentのinitに到達し得る場合は証明保留とする。分岐では差集合の和、直接callはcallee解析を使う。
2. imports/start/threads、間接call、未対応命令、再帰、未対応制御構造は安全側に保留する。未知を同値と数えない。
3. 全APIで残った差を読まないと確認できれば、他のguest状態が等しいという前提の下で、任意長の元API呼び出し列についてsegment差による観測相違がない、という限定的な証明条件を出力する。
4. 同一元binaryの別instanceに実測guest memory/table/segmentを再構成する。追加drop helperは準備専用とし、その後の証拠列は元exportだけに制限する。探索で証拠がないことを証明扱いしない。
5. `wasm-migrate`の保存用memoryや再開selectorは元program状態に含めない。これは**元programの二つのguest状態の比較**であり、変換済み実装の全API継続が正しいという証明ではない。再入可能性の契約を確認せず上流の不具合を追加計上しない。

## 比較と反証

完全state equality、実行したentryのみ、元APIの証拠/証明という三種類の判定を比較する。追加の手製controlでbranch、直接call、未対応間接callを検査し、NodeとWasmtimeで証拠を再生する。

使う基本原理は通常のdef-use解析、状態の観測同値、区別する入力列である。これらを新発明と呼ばない。修士研究の候補は、Wasm復元検査における誤った不具合計上を具体的に分類・再現できる点にある。この実験で強いアルゴリズム的新規性が自動的に成立するわけではない。

## 初回を受けた修正（v2実行前）

v1は14証明条件、2反例、2保留だった。4反例の予測は外れた。最初にcase番号を逆に読んで「共通の先行trapが差を隠す」と説明したが、結果JSONの確認で訂正した（その説明に基づく実装は未実施）。実際の保留はcase 0で、segment 1だけが異なる。元側は最初のinit 1でtrapする。復元側は同じ既存bytesを書き、drop 1を実行し、既に空のsegment 3のinitでtrapする。APIのtrapとmemoryは同じで、segment 1差も消える。case 1はsegment 1/3双方が残り、`test`一回の反例になった。

単なるread-before-drop検査はこの状態依存の一致を証明できない。追加の限定的検査では、各exportの動作が(1)引数なし・有限の既知bulk演算のみ、または(2)副作用なしの単一byte読取りである場合に限り、実測guest状態対から全APIの遷移閉包を構成する。各遷移のAPI結果/可視stateが等しく、差の残る後続状態対が既出なら閉包とする。byte読取りは等しいmemoryからの読取りなので任意i32引数をまとめる。他の形や状態数上限では保留。実行ベースの有限モデル検査であり、一般Wasmの証明とはしない。v2では16限定証明条件・2反例を予測する。既知のbisimulation/モデル検査の応用であり新原理と呼ばない。
