# 実測結果、解析費用、失敗原因

2026-10-19。主系列は`carry-weave-v2`。全件回復という事実だけで不採用にしない。解析本体の時間増加を認めた上で、同コストでの既存難読化に対する優位性、独立した新規性、実アプリケーションでの有用性が未確認であることを記録する。

## 正当性と追加条件

主実験は項数16/32/64、3種類のrotate・xor・mulを含む総和、plain/packed/csa/splitadd/splitcsa、raw/O3の90条件。各対象に回復版も生成した。3系列×3項数の合成問題で、9つの独立した実アプリケーションとは数えない。各モデルの係数seedは一つ、mask・配置seedは37のみ。

入力は境界値9×9=81組とrandom2,048組。元・対象・回復の各版を同じ独立JS oracleと比較した。元問題の入力は3個のi32で、出力はi32一つ。memoryとtrapは対象profileに存在せず、状態副作用を検査した結果ではない。

|追加Node差分|4/5/7/128項の40条件、255,480呼出し、不一致0|[追加結果](../../results/invention-20261019/carry-weave-controls-v2/summary.json)|

全てWABT validationを通した上で評価した。有限試験と縮小モデルは、32bit全入力に対する変換器全体の形式証明ではない。主・追加の呼出しを合わせると830,310回だが、再実行や旧系列をさらに足して標本数を大きく見せない。

## 回復と追加反証

主90/90、追加40/40で元の加算項の多重集合を回復した。回復先は元の加算順を再現する必要がない。同一モデルの全方式が、plainを正規化した回復先とbyte一致することも監査する。未変換自体の読込み・項抽出を同じ解析器で測った。

主の各対象を5回処理した計450解析で、splitcsaの回復本体中央値は0.637–3.958ms。読込み・検証・WAT解析・scalar式DAGへの持上げは別枠で27.090–34.288ms。回復時間には保存則の逆適用、mask結合、出力式の文字列生成を含み、回復Wasmのcompileは含まない。

|比較|回復本体の時間比|
|---|---:|
|splitcsa / plain|2.396–4.112|
|splitcsa / csa|1.756–2.057|
|splitcsa / splitadd|2.006–3.528|

読込み込みのsplitcsa/csa比は0.950–1.182。これは読込みの固定費を含む値で、回復本体の増加がないという意味ではない。[解析生データ](../../results/invention-20261019/carry-weave-performance-v2/analysis.json)、[条件別比](../../results/invention-20261019/carry-weave-report-v2/attack-ratios.json)を保存した。

追加実験の初版では5/7項のsplitcsa raw/O3の4条件が元項まで戻らなかった。零paddingで3入力圧縮が2入力のhalf-adderへ退化していたのが原因で、回復器へ零の正規化と2入力保存則を加えると4件とも回復した。これを保護成功や最適化器のクラッシュとは扱わない。初版の回復版も値は一致していたが、元項回復課題は未達だった。

出力の全和という観測から、圧縮器の両出力を同時に戻せる。分割片の配置を変えても逆順の保存則適用は妨げられない。[アルゴリズム](algorithm.md)で成立条件を説明する。人間の解析時間・専用器の開発時間は未計測。CoBRA、SiMBA、NotDec等は今回実行しておらず、他ツールの未対応を耐性へ計上しない。

## 系列・保守記録

- `probe-v1`は式をmodule専用parserへ直接渡して中断した。回復器の出力処理不備であり耐性ではない。
- `probe-v2`ではO3の定数subや可換引数順に採点用正規化が未対応。式の値は一致した。正規化を修正して主系列へ進んだ。
- 主`v1`は全90件を回復。追加`controls-v1`でzero-paddingの不足を発見した。
- `v2`と`controls-v2`は修正後。解析器が変わったため性能を`performance-v2`で再測定した。旧性能を主値に混ぜない。
- `verify-v2`は入力hashを記録する版で再検証した。再現監査は[summary](../../results/invention-20261019/carry-weave-audit-v1/summary.json)を参照。

## 採否と次の制約

解析本体の定数倍増加は確認した。しかし、圧縮器を一つずつ戻す解析で足り、bitvector全域探索を強制できない。配置規則も既知恒等式の組合せを越える独立した計画算法として確立していない。この候補は主発明として不採用とする。

次に同系統を考えるなら、全出力が同じ重みの和へ閉じていることを先に検査する。保存量が解析者の課題そのものである変換では、局所構文を離しても全体の保存則が回復手順を与える。異なる観測へ変えるだけで新規性が得られるとは限らず、意味保存と既知のデータ表現変換との差を再検査する必要がある。
