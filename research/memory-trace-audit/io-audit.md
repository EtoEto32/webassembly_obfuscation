# 公開APIだけによる接続回復と評価目標の訂正

2026-10-18。前回のメモリ接続対照について、内部計測より弱い攻撃条件を追加した。**27条件すべてで、公開関数の返り値とtrapだけから全payloadと全接続を回復できた。** このAPIを保存する難読化に対して、これらの情報を隠すことを要求するのは適切でない。新しい難読化方式の成果でも、一般のデータ構造を回復する新攻撃の主張でもない。

## 公開契約と攻撃者

対照の`run(i,k)`は公開index `i`から最大`k & 255`ノードをたどる。初期値0に対して各payloadを`rotl32(acc,5) XOR payload`で畳み込み、nullで終了する。indexの範囲外判定は巡回回数の判定より先に行う。

攻撃器`attack-io.cjs`が受け取るのは、この関数を呼ぶoracleだけである。Wasmバイト列、内部メモリ、アクセスtrace、ノード数、配置、生成seed、正解グラフは渡さない。ただし上記の関数族と契約は既知である。ホスト側の`check-io.cjs`は実行準備と採点のためバイナリ・manifestを読む。攻撃器との分離はコード上の引数分離であり、OSによる隔離ではない。

まず長さ0の問い合わせで有効indexの範囲を指数探索と二分探索で求める。その後、ノードごとに長さ1、2、必要なら3以上を問い合わせる。実験の既定上限はノード数4,096、長さ8、問い合わせ100,000回、候補frontier 100,000状態。

## なぜ内部計測なしで分かるか

`F_i(k) = run(i,k)`、`R(x) = rotl32(x,5)`、ノード値を`v_i`とする。公開契約より、

```text
v_i = F_i(1)
iの後続がjなら F_i(2) = R(v_i) XOR v_j
iの後続がnullなら F_i(2) = v_i
```

したがって長さ1の返り値で全payloadが分かり、長さ2の返り値で後続の候補集合が得られる。同じpayloadを持つノードがあると一意には決まらない。長さ3以降の問い合わせで、残る候補から作れる経路の出力と矛盾する接続を除く。

同じノードを再訪したときにも候補を自由に選べる経路集合を使うため、探索は真の決定的グラフの挙動を過大近似する。正しい契約・返り値の下では真の接続を除去しない。frontier上限に達した候補は除去せず残す。全候補集合がsingletonになった場合だけ`unique`とする。これは既知の関数族の中の一意性であり、任意のプログラムの元ソースを一意に同定する意味ではない。

```text
N <- 範囲外trapから探索
各iについて v[i] <- oracle(i,1)
各iについて candidates[i] <- oracle(i,2)と両立する全後続（nullを含む）
長さk = 3..8について:
    oracle(i,k)を全iで問い合わせる
    出力と両立する候補経路がない接続を、変化がなくなるまで除く
    全集合がsingletonなら終了
曖昧な集合は曖昧なまま返す
```

長さ3の照合までで今回の3グラフはすべて一意になった。これは一般のグラフに対する3問い合わせ長の十分性定理ではない。

## 実測結果

結果は[`memory-io-v1/results.json`](../../results/invention-20261018/memory-io-v1/results.json)。未計測の3構造×3表現×raw/O2/O3、計27条件を対象とした。問い合わせ履歴、候補集合、生成したcloneのWAT/Wasm、hash、実験時のコードsnapshotも同じ出力先に保存した。

|元グラフ|各バイナリの問い合わせ回数|長さ2時点の一意な後続|長さ3時点|clone照合入力数／条件|
|---|---:|---:|---:|---:|
|chain48|157|42 / 48|48 / 48|12,316|
|cycle96|303|88 / 96|96 / 96|24,604|
|chain128|399|114 / 128|128 / 128|32,796|

- 27 / 27条件で全payloadと、nullを含む全後続を正しく回復した。集計は各2,448件。元グラフは3つであり、27個の独立した未知グラフではない。
- 総問い合わせ7,731回。問い合わせ長の最大値は3。内部計測を必要としない。
- 学習したindex間の接続と値から、新しい8byteレコード配置のWasm cloneを生成した。元バイナリや元の物理アドレスを再利用しない。27 cloneをWABTでvalidateした。
- 元とcloneを、全有効index×256通りの有効長に加え、範囲外index・長さの上位bitを含む入力で照合した。計627,444入力条件、1,254,888実行で不一致0。条件間の入力再利用を含み、独立入力が125万個という意味ではない。
- 全payloadが0の3ノード対照では、nullを含む4候補が全ノードに残り、`ambiguous`となった。区別不能な元グラフを勝手に選んで回復成功としないことを確認した。

有効長と有効indexの組を全列挙したこと、境界入力を試したこと、契約からの推論は区別する。今回の有限実行を、変換器や任意Wasmの全入力に対する形式証明とはしない。時間はoracle呼出しを含む単発の診断値で、コンパイルとclone検査を除く。反復性能・RSS・実用攻撃費用の比較は行っていない。

## 前回の解釈の訂正

前回は、配置やpointerの値を変えてもアクセス順から接続を回復できるため、「次の候補では巡回を変える必要がある」と解釈した。**この対照では公開API自体が接続を開示するので、巡回の変更だけでは問題を解決できない。** 同じ公開挙動を保つ変換には同じ問い合わせ列と返り値が成立し、今回の回復がそのまま適用できる。変換によって1回の実行時間が増える可能性はあるが、問い合わせ数は減らせない。

前回の計測器の正当性検査とアクセス列からの回復結果は取り消さない。この対照の用途を、計測・攻撃実装の動作確認に限定する。これだけを使い、難読化が保護すべき情報を守れたかの主評価や、新候補一般の採用判断にはしない。

次の実験では、実用目的から公開APIと保護対象を先に固定し、公開I/Oのみでの回復費用を測る。任意の開始ノード・内部の巡回回数・正解中間値を渡す便宜的なAPIを本来の公開ABIと混同しない。公開情報だけで安く復元できる対象なら、その対象に関する難読化の成功条件を設けない。APIを弱めて好結果を作るのではなく、実際の用途で保護する価値と可能性のある対象を選ぶ。

この結果は一般の難読化の不可能性証明ではなく、この契約と3グラフに対する回復の上界である。新しい変換規則は未確定であり、研究全体は継続中。
