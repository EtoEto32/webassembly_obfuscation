# 論文追補：現状態から修復できる表現の生成

## Abstract

符号化したWasmのcopy列について、コピーが失う情報の列に適合する表現を生成し、入口保存値を使わずに全正常・trap出口の状態を修復する限定変換を実装した。3つの固定構造で正当性を検査し、同じ表現の入口共有基底保存に比べて正常実行の中央値が2構造で26～28%減少、1構造で2.8%増加した。既存回復器は全12保護条件を復元し、独立した新規性と保護上の優位は未確立である。

## Motivation / Proposed Method

以前の方式は全prefixの差分が必要とする入口の線形基底を保存した。この最小性は現在のmemoryを参照しない条件付きだった。今回はkernelの保存条件から、現memoryを副情報として用いる修復可能性を直接検査する。prefix行列Pに対しker(P)⊆ker(B P B^-1)を要求し、copyで消える元位置の順序からblock三角のBを生成する。現memoryの代表位置を選ぶQを使い、W=(B P B^-1+P)Q、W P=B P B^-1+Pを検査し、y←y+W yで修復する。

## Related Work / Threat Model

OSRの値再構成とmemory補償、Backstrokeの値回復関係、Data Randomizationの制約に基づく表現選択が近い先行技術である。写像の因子化とblock三角構造は新しい一般原理ではない。Wasm固有性は範囲検査が書込みに先行するcopyのtrap意味を利用する点にあり、数学自体は他形式にも適用できる。全binaryと方式を知る解析者による、通常byte表現とcopy列の等価Wasm回復を保護対象にした。

## Implementation / Evaluation

実wasmをWABTで読み、閉じたcopy profileとのAST一致を確認するPython生成器を実装。54条件83,196呼出しで不一致0、42,588の期待trapを含む。WABT別実行器360呼出し、1,404 memory probe、66本のbyte再現が一致。小モデルは107,520状態対で生成条件と修復を確認。これを一般プログラムの機械証明とは扱わない。

別module import、36 fresh process、252batchで正常実行を測定。同じBのbasisに対するcurrent比は1.028、0.737、0.722。元版に対しては2.104、2.809、1.648倍。コードは全3構造で大きくなり、線形memoryは全て64KiB。入口から保持する値は3/21/20個から0へ減ったが、出口の修復用localは残る。

## Discussion / Limitations / Conclusion

既存のbinary-only回復器が未変更で12/12条件を元binaryへ復元した。方式既知の回復の中央値は同じBのbasis対照に対してほぼ同じか低く、追加保護効果は支持されない。公開digest内の復号式とnative copyが変わらず、保存戦略の変更が回復に必要な情報を減らしていないことが原因である。少数の固定copy構造・正常経路だけの性能評価から一般アプリへ外挿しない。保存・修復費用の改善部品として保持し、独立した主難読化発明には採用しない。
