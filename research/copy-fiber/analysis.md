# 実際の圧縮計算でも消去できた非線形表現

2026-10-21。事前の[計画](plan.md)に従い、公開状態APIを持たない全64roundの
SHA-256圧縮に適用した。主結果はmain-v1、recovery-v1、runtime-v1、audit-v3。

## 正当性

5構成×raw/O3の10条件。共通262個の圧縮入力を各版へ渡し2,620比較、同じ41個の
メッセージから完全SHAを計算し410比較で不一致0。境界値・固定seed入力と
Node cryptoを用い、同じinstanceを繰返し呼ぶ。診断版では16入力×10条件について
H保持、Wの表現関係、64byte以外のmemoryが零のままであることを確認した。
主コーパスのhashはchecks.jsonに保存。全入力の機械証明ではない。

回復した10本と各O3版の20条件も、圧縮5,240比較と完全SHA820比較で不一致0。
これは同じ入力の再利用で、独立した786入力や123個のメッセージではない。
1条件のhash内で複数回呼ぶcompressを別途の試験件数に加えていない。

2bit×3座標の4,096状態pairを全列挙し逆変換・copy互換を確認。32bitの逆変換を
100組照合し、gの非線形性の具体的反例を保存。g(0)をずらす誤実装と逆順を壊した
誤実装のraw/O3計4本で、実際にSHA圧縮の不一致を検出した。正当なWasmだが
範囲外profileの3入力は変換器が拒否した。

最終ソースから主10本を再生成してbyte一致。WABT interpreterとNodeの独立参照で
O3主5本＋回復1本の1入力ずつを照合した。別engineの範囲を主コーパスと混同しない。

## 攻撃モデルと解析結果

解析者は配布Wasmと方式の設計を知り、係数を秘密としない。公開compressを利用でき、
binaryの読取り・書換え・専用解析器の開発も可能。元の状態read/write APIは存在しない。
目的は、表現を取り除いた同等の計算を構成するための負担を増すこと。

recover.pyは実Wasmだけを読み、codecのseed・元SHAソース・デバッグ情報を入力に
していない。entry memoryを未定にしても出力依存は消え、全10条件で1,881演算の
同じ記号DAGへ到達した。全出力のcanonical fingerprintが一致する。raw生成物は
ローカルの順序等により4種類のbyte列になるので「10本ともbyte一致」とは言わない。
8本の変換条件のうちunsupported/error/timeoutは0。

解除本体の単発測定は、plain約19–20ms、非線形1層約373–441ms、2層約665–768ms。
WABT読取り、Wasm再コンパイルとO3は別項目。反復統計ではなく、初見の人間の解析時間や
解析器の開発費用も測っていない。解析負担の増加自体を否定しないが、すべて1秒未満で
同じ計算へ戻り、層の追加は実行費用も増やした。

SHAは公開の標準アルゴリズムなので、その意味を知る解析者は独立実装で置き換える
さらに簡単な方法もある。本試験はSHAという機能の秘匿を証明するものではなく、
小さい公開状態APIがない実計算に入れても一般の記号相殺で表現を取り除けるかの
検査である。非公開業務アルゴリズム一般の解析時間へ外挿しない。

## 性能とアブレーション

Windows、Node24.15.0/V8、WABT1.0.42、Binaryen133。O3のcoreへ共通のWasm内loopを
後付けし、その後のwasm-optは行わない。JITの機械語は監査していない。入力のchaining
stateを前回出力から更新しblockも変える。warmup32回×32圧縮、10msを目標に最大65,536
反復までcalibrate、7batch、条件ごと3fresh process、seed211054で順序を混ぜた。
18processの共通257反復checksumは一致。RSSはNode全体で、codec単独ではない。

| O3構成 | 圧縮1回の中央値 ns | 3process中央値の最小–最大 ns | core bytes | linear memory |
|---|---:|---:|---:|---:|
| plain | 254.97 | 250.22–257.56 | 13,552 | 65,536 |
| 線形native | 4,846.02 | 4,786.04–4,893.70 | 15,418 | 65,536 |
| 非線形1層native | 5,984.72 | 5,863.96–6,069.97 | 16,547 | 65,536 |
| 非線形2層native | 11,400.88 | 11,301.07–11,581.74 | 20,061 | 65,536 |
| 非線形1層repair | 6,177.73 | 6,142.19–6,372.46 | 16,987 | 65,536 |
| 回復版 | 182.48 | 177.18–182.90 | 7,603 | 0 |

非線形1層nativeはrepairより約3.12%短く440bytes小さいが、plainより約23.47倍遅い。
回復版はprivate memoryの読書きを消せるのでplainよりも短い。これはSHA全ハッシュや
一般逆コンパイラの速度ではない。rangeを信頼区間とは扱わない。

repairは同じgについてcopy前後で全体を復号・再符号化する素朴な自作対照。
初期コピー前のWは死んでいるため、その復号まで行う対照は最適ではない。
最良の既存方式やWASMixerに勝った比較ではない。コピー密度は1回/64roundであり、
小さいAPI workloadで見えた大きなcopy費用改善を実計算へ持ち込めなかった。

linear/native/nonlinear/layersの差を分けたが、8語を各storeで全復号する実装自体は
高価である。既知の依存cone最適化で軽量化できる可能性はある。しかし今回の相殺を
防ぐ根拠にはならないため、係数や層数を増やす探索・追加性能測定には進まなかった。
変換時間は4構成の単発で約69–73ms、WABT読取り・コンパイルを含む。統計ではない。

## 判断と次の制約

native copyを保つ非線形な生成規則と、公開状態APIのない実装・解除・測定を得た。
しかし独立した新規性と有用な保護効果の成功条件は満たさず、主案には採用しない。
有限環残差方式の既存の構成的提案は保持する。

前の失敗原因は公開APIだけではなかった。各storeの末尾でgを評価し、次のloadで
g^-1を評価する構造を、アドレスの追跡とXOR相殺で横断できる。次候補には
この安い分離を避ける具体的な演算変換が必要。単にgを非線形・多層にする、
内部APIを隠す、helperをinlineするだけでは、今回の記号解析への回答にならない。
また融合による対処そのものもEOC等に先行し、その一般着想を発明として数えない。

初回audit-v1は括弧のsyntax errorで未開始。v2は「同じDAGなら生成binaryも同一」と
する過剰なassertionで停止。意味fingerprintとbyte再現を分けたv3を主監査とし、
失敗source・理由を保存した。失敗を解析耐性に加算していない。
