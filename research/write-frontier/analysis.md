# 失敗境界ごとの書込み再配置

## 保護目標と制約

元フィールド境界に沿うstore列を異なる幅・位置・順序のstoreへ変え、何をどこへ更新するかの回復費用を増やす、という仮説を検査した。元の非観測な実行順序を当てる課題にはしない。解析者は方式と全バイナリを知り、公開memoryと引数も利用できる。秘密鍵、暗号化された実行領域、検出回避は使わない。

入力制限は[README](README.md)に記す。値が引数のbyteに限定される点は、後述の公開I/O解析に決定的である。

## アルゴリズム

store_iの即値offsetをo_i、byte幅をw_i、右端をR_i=o_i+w_iとする。新しい最大R_iが現れるたびに区間を開始し、区間ごとに最終的なbyteの由来を、元の順序の上書きとして計算する。由来は `(引数番号, 引数内byte位置)`。元storeが書かない穴は埋めない。

各連続byte区間に対して、幅1/2/4/8のstoreで被覆を作る。重なる部分は同じ最終値を書く。最初のstoreはその区間の右端へ達するものに限定し、一番大きな右端を持つ連続区間を先に出力する。後続storeは既知のseedで順序を混ぜられる。

通常被覆は、区間に収まる最大幅wを選び、右端側からwずつ被覆し、左端の余りでは重ねて書く。必要数ceil(length/w)は、この条件での下界に一致する。幅1–12byteについて独立な集合BFSで最小数を確認した。

境界優先被覆は、最初のstore候補を列挙した後、残りを左から被覆する動的計画法で、store内に含まれる異なる引数の境界数を最大化する。`woven0` は通常被覆のstore数を上限、`woven1` は各連続区間で+1を上限とする。予算を使い切るとは限らない。`random1` はwoven1が実際に使ったstore数に合わせ、許容される被覆から乱択する。同store数は同じ実行時間を意味しないので実測も比較する。境界数は同じ境界を複数回数えることがあり、解析耐性の代理指標にとどまる。

```
groups = split_at_new_maximum(offset + width)
for group in groups:
    image = apply_original_stores_in_order(group)
    for contiguous_run in image, largest_right_endpoint_first:
        choose anchor ending at this run's right endpoint
        choose remaining intervals under a store budget
        pack each interval's final bytes from the input arguments
    emit anchor at the group's largest endpoint first
    emit the remaining packed stores
```

## 意味保存

memory長をM、baseのunsigned値をpとすると、元store_iが成功する条件は数学的な整数加算で `p+R_i≤M`。baseと即値offsetの和をi32の折返し加算へ置換していない。ある区間の先頭storeが成功すれば、同区間の右端はすべてそれ以下なので残りも成功する。変換後の最初のstoreも同じ最大右端を持つため、区間を全く書かずにtrapする条件が同じになる。

区間内では値の計算にtrap・副作用がなく、共有memoryや外部観測もない。全storeが成功する場合、各byteに同じ最終値を書き、穴を保持する。区間単位の帰納で、正常終了と最初のtrapの両方でmemoryと返り値が一致する。trapのPC・命令幅・スタックトレースは保存対象外。

この限定アルゴリズムの説明と、実装全体の機械検証済み証明は別である。validator、2種類の記号的byte抽出、独立な実行モデル、Node/WABTの差分実行を使った。有限試験を全入力の証明とはしない。

誤った全体融合は、残り6byteの位置で元の最初の4byte書込みを失った。誤った下位byteからの分割は、残り14byteの位置で元なら失敗して何も書かない4byte storeの先頭2byteを書いてしまった。両方ともtrap有無は同じであり、trap有無だけの比較では発見できない。

## 静的解析

WABT出力を読み、定数shift、mask、OR、拡張・切詰め、限定的な非重複加算を記号評価する。最初はbit単位、次にbyte単位へ軽量化した。各storeのbyteの由来を求め、同じ右端最大値の規則で区間へ戻し、簡潔な広幅store列を出力する。元ソース・生成時の被覆・seedは使用しない。採点だけが元の区間像を参照する。

raw/O2/O3の全72条件を両解析で回復し、回復Wasmも検証した。最終主条件では未対応・crash・timeout・誤答は各0。これは限定族の成績であり、汎用Wasm解析器の成績ではない。

## 公開I/Oだけを使う解析

すべての引数byteへ異なるラベル値1–124を与え、memoryを255で初期化する。最大footprintが256byte以下という既知の対象条件を使い、残容量256byteのbaseで1回実行する。書かれたラベルから、最終memoryのbyteの由来と最大右端Rを読む。

次に残容量R-1のbaseで同じ入力を実行する。最後の区間はtrapするため、その直前までのmemoryが公開される。残った最大右端を次のRとして繰り返す。区間数gに対してg+1回で各累積像が分かり、前後の差から必要な更新を生成できる。

| カーネル | 失敗境界 | 問い合わせ/バイナリ |
|---|---|---:|
| increasing | 4,8,12,16 | 5 |
| descending | 16 | 2 |
| zigzag | 16,32 | 3 |
| overlap | 16,24 | 3 |

72本を計234問い合わせで学習し、72 cloneを別の境界値・乱数入力で82,098回実行して不一致0だった。命令を検査せずexportだけを使う。学習器は「値が引数byteのコピー」という事前知識に依存する。一般の計算、条件付き書込み、任意の定数変換を1組のラベル入力で同定できると主張しない。

この解析ではwovenも対照も問い合わせ数が同じだった。公開APIが直接与える情報を、内部のstore配置だけで隠すという保護目標の弱さが判明した。コードの見た目が変わることと、利用可能な意味を取得する費用は別である。

## 正当性・実行環境

4カーネル×6方式×raw/O2/O3=72主条件、静的回復72本。Nodeの164,196呼出しで値・trap有無・全64KiB memoryを比較し不一致0、trapは70,632回。各カーネルの境界集合は各store右端の直前・一致・直後と大きなunsigned base、5種の整数境界値を含み、さらに1,024乱数入力を使った。入力数はカーネルごとに異なる。初期memoryを毎回戻している。

WABTでは144本それぞれに正常入力と境界入力を1回ずつ与え、writer 288回の後、公開memoryの末尾56byteを読み出した。trap後も読取りを継続し、計16,128回のmemory読取りが期待値と一致した。Binaryenは最適化だけに使用した。

400個の異なるstoreモデルに対して5方式・66base位置、計132,000比較も一致。これは追加Wasm件数ではない。最大幅の被覆数は小幅の独立BFSで確認した。load値、別base、base変更を持つ有効Wasmは変換器が拒否した。

環境はWindows、Python3.9.0、Node24.15.0/V8 13.6、WABT1.0.42、Binaryen133、Core i9-11900K。主実験の再実行で144バイナリのbyte一致を確認した。

## 判断

Wasmの正確なtrap後のmemoryを保つ被覆規則として動作し、一部の静的解析費用は増えた。この結果をゼロとはしない。しかし、同じ制約が安い正規化を与え、公開I/Oでの回復問い合わせも増えず、store merging・正確な例外の先行技術との差が小さい。今回の限定方式は主発明に採用しない。

未実施事項は、汎用プログラムの変換、実際の逆コンパイラでの型回復、人の解析時間、一般の式を含む更新、網羅的な公報調査、全Wasm実装の形式証明。次の候補では、APIから少数のラベル入力で直接得られるコピー関係を保護目標に選ばない。
